# Feedback and revision

## Load when
Writing issues, setting severity, or verifying Noni's single permitted revision.

## Questions answered
Can Noni act on this issue without guessing? Was each prior issue genuinely resolved?

## Method
1. Name one observable defect, its reader or policy consequence, and the required correction outcome.
2. Target one permitted field path and the matching editorial dimension.
3. Cite only evidence and constraints necessary to understand the defect.
4. Do not provide replacement wording, alternatives, or a second candidate.
5. Set severity by consequence: high blocks grounding or safety; medium blocks the assigned job; low is material polish.
6. On revision, compare each prior issue against the new field value and list exactly resolved IDs.
7. Do not introduce discretionary new issues on the final pass unless the revision itself created a contract violation.

## Required inputs
Current draft, pass type, prior draft and review when present, evidence, and constraints.

## Expected contract effect
Actionable bounded issues or exact complete issue resolution.

## Failure modes
Vague instructions, bundled defects, solution copy, invented IDs, moving goalposts, or requesting a third automatic pass.

## Evidence and authority
Feedback proposes corrections only. Deterministic code owns loop limits, review metadata, and workflow state.
